# Sparrow 非阻断问题与优化清单

更新日期：2026-09-19。已提交核对基线：`1dd17c8`（含 K3/K4）；后续 Core-A/B1/B2-A、K1～K4 组合完善与时间型 Preview 的新增证据单独标明，均未提交。

K3/K4 历史条目按各自匹配构建解释；后续条目链接对应 Core-A/B1/B2-A 候选证据，不把未提交的新代码混称为已提交基线。

这是项目长期维护的优化清单，不是某一轮 review 报告。集中记录**在当前适用范围内不阻断使用，但有性能、资源、时效或维护成本问题**的项目，后续可以按模块成批处理。

“非阻断”有前提，并不表示没有影响，也不代表已经通过生产认证。若实际部署必须满足某项容量/时效，而当前达不到，就不能继续把它当作可延期优化。

## 1. 收录与维护规则

- **收录**：已观察到的性能问题、明确的资源/时效取舍、已有证据的重复开销及待量化优化候选。区分“已测现象”“代码确认”“待验证假设”，不把推测写成根因。
- **不收录为普通优化**：结果错误、数据丢失/损坏、越过提交点 ACK、恢复错误、安全问题、死锁或无界资源增长；发现后升级为修复任务，不能等统一优化。
- **另外管理**：TLS/网络/设备/长稳等生产验证缺口，以及尚未实现的新功能，仍在 [开发 TODO §8.4](DEVELOPMENT_TODO.md#k2-followups)。它们不因移出本文件而消失。
- 编号 `OPT-001` 起永久保留、不复用；旧任务号仅作为关联，**优化明细以本文件为唯一维护位置**。每次 review 后补充或更新，不另开一份散落的优化 MD。
- 状态使用“待优化 / 待量化 / 进行中 / 已解决 / 暂不采用”；未安排的负责人均为待认领，排期在开工时确认。不因登记即开始实施。
- 完成时在原条目追加修复 commit、对照结果和回归证据；不直接删除历史。若决定不做，记录理由与适用限制。

### 2.1 JetStream 接入链路

<a id="opt-001"></a>
#### OPT-001 — 10k 档积压与尾延迟

- **现象/证据**：8190 条 paced 短测中，零状态/单 Count 实际到 HTTP 约 7952/6861 输入/s，p99 约 436/460 ms；该试次输出完整，但有积压。预装排空约 19.9k/12.2k 输入/s 不包含生产者写盘，不能当作持续接入能力。见 [R12 基线](JETSTREAM.md#r12-validation)。
- **待办**：分离生产者、broker 持久写入、pull/解码/执行、checkpoint、ACK 和 HTTP 的耗时/排队，固定介质、schema、预算与输出合同做阶梯 rate sweep；根因尚未确定，不能直接归咎于内核或 broker。
- **验收**：开跑前定义目标负载、p99 和积压阈值；记录实际发布/处理/提交速率、队列年龄与增长、排空时间、CPU/RSS/I/O。核对输出/ID/状态与 ACK cut，保留失败样本；不靠放大队列、弱化 durability 或删除保护制造提升。
- **关联/升级条件**：原 `K2-OPT-01`；REL-02/03、HTTP-05/06、QA-07。若部署必须持续 10k/s 且低延迟，或积压逼近保留范围，本项就是该部署的上线阻断项。

<a id="opt-002"></a>
#### OPT-002 — 默认 4 MiB 预算下的消息容量

- **现象/证据**：SDK 预留约 2.8 MiB、ACK 工作区 64 KiB，原始记录和解码 scratch 同时存活；基础额度推导的乐观 payload 上界已低于 10 KiB，实际还受 schema/批次/状态/HTTP 占用影响。协议允许 64 KiB 不代表宿主能接纳。见 [资源合同](JETSTREAM.md#broker-与资源前置)。
- **待办**：提供可复验的消息/schema 容量档位和准入提示，再评估更紧的结构化解码估算、减少拷贝或显式宿主预算 profile；不移除 headers 展开、Bytes pin、稀疏字段的额度保护。
- **验收**：消息大小边界、稀疏/深层 JSON、长字段、headers、并发编码/冻结的成功及拒绝反例；核对峰值预算/RSS、超限不 ACK、停止后资源释放。没有实测的消息大小不列为 Supported。
- **关联/升级条件**：原 `K2-OPT-02`；REL-02、MEM、FMT-01。若实际业务消息在默认预算下被拒绝，必须先解决该容量要求，不能笼统说“不影响使用”。

<a id="opt-003"></a>
#### OPT-003 — 空闲首消息等待

- **现象/证据**：当前空拉取使用 5～250 ms 退避，降低空闲 broker 请求量；空闲后的首消息可能额外等待约 250 ms，并非所有消息都增加该延迟。见 [R12 执行形态](JETSTREAM.md#r12-执行形态)。
- **待办**：比较有界可配置退避与受控长轮询；保留 SDK 已缓冲帧以及控制/ACK/取消进展，不重新引入计时器先于缓冲数据的问题。
- **验收**：空闲后单条、低频、突发和持续负载分别测首消息/p99、pull 请求率、CPU、取消耗时及内存；明确时效和资源之间的取舍。
- **关联/升级条件**：原 `K2-OPT-03`；AGE、REL-02。若告警等业务不能接受该唤醒等待，须先处理再宣称满足时效。

<a id="opt-004"></a>
#### OPT-004 — 远端控制查询与 ACK 调度成本

- **现象/证据**：完整 verify 含 stream info、KV policy、binding 三个控制查询；Explicit ACK 已为 16 路并发。代码中的查询成本已知，但真实高 RTT 下的收益/瓶颈尚未量化，不能标成已证实的远端故障。
- **待办**：测不同 RTT、pending/pull、checkpoint 周期与慢 Sink；确认收益后再考虑验证频率/缓存或 ACK 调度。不能直接替换成 AckAll，或省略所有权/保留范围检查。
- **验收**：改善实测吞吐/时效且控制流仍有进展；旧 token、重投递、ACK 丢失/负响应、运行期策略变更、取消与资源回收均通过，ACK 不越过 durable cut。
- **关联/升级条件**：原 `K2-OPT-04`；REL-03/06/10、HTTP-05。未验证的网络 profile 不因本项是优化候选就自动获得生产支持。

### 2.2 既有内核与控制面的优化候选

以下三项由 [R11 后续优化记录](PRODUCTION.md#r11-validation) 迁入统一清单；不是重新打开已修复的正确性问题，收益仍需量化。

<a id="opt-005"></a>
#### OPT-005 — MIN/MAX 分组 key 构造与查表复用

- **现状**：已有候选 Vec 复用、获胜值 detach 及 key 字节计费缓存；这些不重做。后续仅评估重复分组 key 的构造、编码和查表是否值得在批内复用。入口：`crates/sparrow-runtime/src/window.rs`、`crates/sparrow-runtime/src/state.rs`。
- **待办/验收**：先用多 key、宽 key、变长 MIN/MAX profile 定位剩余分配/查表热点，再做有界复用；对照 CPU、分配数、吞吐/p99/RSS。保持 NULL/比较/窗口顺序、快照结果、key 预算和取消/错误时资源结算不变。
- **可延后原因**：属于 CPU/分配优化候选，未据此发现结果错误；不承诺所有 workload 都能获益。关联 MEM、STATE、QA-07。

<a id="opt-006"></a>
#### OPT-006 — checkpoint 上一代校验与 GC 读 I/O

- **现状**：提交路径仍加载/校验上一代以保护 publication 与恢复/GC 边界，可能增加大状态或高频提交的读 I/O。入口：`crates/sparrow-runtime/src/checkpoint.rs` 的 `commit_bytes` / `load_generation_mode`。
- **待办/验收**：测状态大小、checkpoint 频率与不同介质下的读量和提交耗时，再评估有界缓存及失效规则；不能把诊断头缓存当 CRC/提交证明。保留损坏、替换、进程重启、落盘失败和 GC/pin 反例，不能为了减少 I/O 保护错误的恢复点。
- **可延后原因**：当前校验是保守安全路径，主要待确认其性能成本；若不能满足部署恢复点时效，则升级处理。关联 STATE、OPS-04、QA-09。

<a id="opt-007"></a>
#### OPT-007 — held 规则的 catalog 重复读取

- **现状**：收敛循环对 held 规则仍读取实际/期望状态，部分路径还读取配置 revision，以判断固定恢复和重新启动资格。入口：`crates/sparrow-control/src/supervisor.rs` 的 `actual_if_start_allowed`。
- **待办/验收**：测 held 规则增多时的 SQLite 查询量和控制面延迟，再考虑 revision/事件驱动的有界缓存；覆盖显式 start、stop/update、safe-mode、失败原因和重启后缓存失效。不得因缓存陈旧自动解锁 held、误用旧配置或丢失错误信息。
- **可延后原因**：主要是控制面开销，不能在没有热点证据时先增加缓存复杂度。关联 OPS、PUB、QA-06/07。

### 2.3 DAG 执行

<a id="opt-008"></a>
### OPT-008 — DAG Sink 失败观察的空闲轮询

- **现象/证据**：K3 `kernel.rs` 的图 Sink 在等待数据时，每 10 ms 检查自己的失败计数，保证上游安静时也能结束 required 失败 attempt。即使没有在途 HTTP，也会轮询；每个空闲 Sink 理论上约 100 次检查/s，实际 CPU/系统唤醒成本尚未单独量化。旧线性路径绕过这个 select 分支。
- **待办**：先测 1/多图、多 Sink 的 idle CPU/唤醒量，再考虑 `InflightCounter` 的有界通知或等效机制，不能用“不再检查失败”省开销。
- **验收**：覆盖失败发生在注册前/注册中/等待中、空闲后单批失败、取消、丢弃与 ACK 并发、EOF 最终 flush；不得丢失唤醒或把 required 失败当健康。对照空闲 CPU、吞吐、错误可见延迟及 stop/join 资源释放。
- **可延后前提**：当前规模 CPU/时效可接受；这是观察方式的成本，不是已知丢数据或 checkpoint 错提。如果目标设备/大量空闲图超出 CPU 预算，升级为该部署的放行前置。关联 DAG-05、OBS、QA-06/07。

<a id="opt-010"></a>
### OPT-010 — 参考表的保守构造/Lookup scratch 配额

- **现状/证据**：B1 loader 在复制前预留 `payload_bytes × 64 + 64 KiB`，还要保留表的 resident/CRC 构造峰值 lease。默认 4 MiB reservation 因此不能保证装入每一个接近 64 KiB 的表；Lookup scratch 还用已选定表的最大行 resident 上界，遇到大但不常命中的行/未保留字段可能提前报配额不足。代码边界确认，收益和典型场景容量尚未量化；不是结果错误或静默丢弃。
- **待办**：按实际 schema、字符串/key/keep/batch 组合测容量，再考虑更紧的、仍在复制前准入的 typed estimate；必要时为选定命中行计费。不得恢复按 wire/logical bytes 冒充 resident 的旧计量，也不得绕过共享 Job owner。
- **验收与可延后前提**：目标表和输入 batch 已经完整通过加载/运行、错误退款与 RSS 检查时可延期。若业务所需表被默认配额拒绝，本项是该部署前置；比较成功边界、拒绝边界和峰值，不通过扩大默认预算制造“优化”。保留 binding SHA、miss/NULL、并发版本选择与取消 guard 的正确性。

<a id="opt-011"></a>
### OPT-011 — 可靠 checkpoint 失败的 API 根因透传

- **状态/优先级**：待优化，诊断体验；不改变提交或ACK合同。
- **现象/证据**：本轮profile10的`CURRENT.tmp`真实I/O故障会结束可靠attempt。API waiter可能先返回`cancelled: job stopping`，实际根因随后保留在`actual.last_error`，含`checkpoint io:`与`is a directory`。见`k1-k4-core-artifacts-20260917/completion-v7d/process`；受保护CURRENT/payload、未提交pending及相同ID恢复均通过。
- **影响/延期前提**：数据正确性路径会fail-closed，不提前ACK；排障需关联API响应和最终pipeline状态，不能把取消本身当作存储错误证明。
- **改进/验收**：考虑在单飞checkpoint完成对象中保留首个决定性错误，再通知取消waiter；区分用户取消、超时和实际存储失败。覆盖失败/stop同时发生、任务join、已有waiter超时后提交完成等竞态，不延迟资源释放，不覆盖先发生的根因或泄漏敏感路径。关联OBS、REL、OPS；未分配解决commit。

<a id="opt-012"></a>
### OPT-012 — 时间型 profile 的逐决策提交成本

- **状态/范围**：待优化；影响时间型 v14～v19。为先证明恢复正确性，当前一个输入行/EOF/空闲 tick 对应一个持久决策和完整 checkpoint，提交前不开放下一决策。它不是旧 v3～v13 高吞吐链路的退化，也不是通用多记录 WAL。功能验收通过不代表该成本已解决。
  - 后续 Alarm v20～22、Silence v23/24 同样采用串行提交，不能继承下方 v14 的容量数字。Silence 没有输出的决策不会等待一个不存在的 HTTP 请求；实际事件的慢 ACK/重试仍阻塞提交，超出观测间隔后下一次观测必须重新建立完整宽限。保持各 profile 已声明的 time/input/fact 顺序，不能为合并提交改变已持久化事实的重放语义。
  - 2026-09-23 v18/v19 已完成限定功能验收，增加所有来源控制、确定性 Union 轮缓冲和全部 required Sink 的等待；下方 v14 数字不外推为图容量。全部来源 EOF 后仍保留逻辑 tick/barrier 服务，后续可在不损害 PT timer、取消和手动 checkpoint 的前提下减少空闲 fsync；当前不作此优化。默认 Union 整轮 256 行与半 reservation 字节上限、大图队列准入也必须计入容量选型，不能外推每算子的 key 上限。
- **实测**：`box@100.64.0.18` 的 `paused-time-artifacts-20260919/process-v4/serialized-cost-{0,20}ms`，File、单 key、Debounce leading-only、每行一个 POST、各 100 行全部持久提交且输出 ID 连续：HTTP 无人工延迟约 **139 行/s**，人工响应延迟 20 ms 约 **34.1 行/s**。这是短程成本观察，不是容量认证或 eKuiper 对照；20 ms 是模拟响应延迟，不是真实 WAN RTT。
- **代码确认/待量化**：每决策 journal fsync、完整 snapshot/目录 fsync、required HTTP flush 均串行；空闲也按配置频率提交 tick。更大状态、多规则、介质写入量和长稳影响还需专项量化，不能仅从本次 100 行推断具体热点占比。
- **方向/验收**：按需求设计有界多决策 journal、group commit/批处理以及有证据的空闲 tick 合并；持久序号、timer-before-input、输出身份、ACK cut、初始 generation、日志保留/GC 和旧 profile 拒绝必须一起验证。不得删除先持久后发布、缩小恢复范围或放大默认预算换吞吐。保持现有正确性/资源/故障门槛，另建预先声明的容量阶梯和真实介质测量。
- **延期前提**：目标规则频率低、状态/展开量、延迟与磁盘预算满足验证时可以使用限定 Preview；如果业务要求持续数千/上万条每秒，或大量空闲规则下的 I/O 不可接受，本项就是该部署的前置，不应表述为“不影响使用”。关联 STATE/REL/HTTP/MEM/QA；未声明时间域/依赖/拓扑等新功能仍留在开发 TODO。v14 的历史数字不能替代 v16～v19 大状态、多规则或真实目标设备容量测量。

## 3. 后续统一处理方式

1. 按模块选一批：例如先做 JetStream 容量/延迟诊断，再单独做 Window/Checkpoint/控制面热点，不把所有候选一次混改。
2. 开工时重新核对当前 commit、适用负载、证据、优先级和验收阈值；历史数字不自动代表新版本。
3. 固定基线、先加反例，再修改和自查；集中编译并复用冻结测试二进制，保留正确性、资源、故障和性能结果。
4. 验收通过才将原条目标为“已解决”；没有收益或风险不合适则记“暂不采用”及理由。生产验证和新功能仍由开发 TODO 独立追踪。

新增条目按同一格式填写：**编号/模块、状态与优先级、现象及证据、影响与可延后前提、改进方向、验收标准、关联任务、解决 commit/结果**。当前尚无已解决归档项。
